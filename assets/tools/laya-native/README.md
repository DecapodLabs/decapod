# Rust-native Laya worker

Laya inference and its external model files remain separate from the Decapod
crate. This worker uses the maintained `laya-onnx` Rust SDK for CPU execution and
a direct Candle implementation for explicit Apple Metal execution. It does not
run Python, generate text, route agents or authorize publication.

This worker is unqualified development work. Native numerical checks pass, but
the pinned upstream profiles failed readiness controls, and the bounded final
affine fit also failed its fitting acceptance. The fitted artifact is private
and inactive; the held-out evaluation remains unscored. See
[`docs/laya-readiness-migration.md`](../../../docs/laya-readiness-migration.md)
for exact evidence and the remaining capability gap. No full validation or
publication success follows from these diagnostic tests.

The initial numerical qualification uses these immutable sources:

- Laya SDK and public reference vectors: [`NandhaKishorM/laya` at
  `7a77439b0923d6efe00052d50a7f787840bfce98`](https://github.com/NandhaKishorM/laya/tree/7a77439b0923d6efe00052d50a7f787840bfce98/laya-rust).
- English SafeTensors: `convaiinnovations/laya` at
  `7b928d828b7b0e022f929d9bd2e44165aa270148`, SHA-256
  `891102d372688fc2a094dac56a384bc537b87c63f21f9f3dac0be2b7cbc8d86c`.
  The export producer's original upstream revision
  `55cf4c4ebb4ebe31b2550e8bdf3bd21b99753851` has the same weight hash.
- Reviewed public split ONNX conversion: [`desplega/laya-onnx` at
  `511bd780d5ab8592bee0a6298fc8c8ab386a268f`](https://huggingface.co/desplega/laya-onnx/tree/511bd780d5ab8592bee0a6298fc8c8ab386a268f/english/fp32).
  This is a community conversion, with its own export provenance and hash
  boundary. It is not presented as an upstream-published ONNX release.
- Candle ModernBERT source: `guoqingbao/candle` at
  `23a6f388a82a71c88067ad2b0d64ac9d00f24aac`; vendored `modernbert.rs` has
  formatting-only adaptation. Candle is MIT/Apache-2.0; Laya is Apache-2.0.
- ONNX Runtime Rust bindings: `ort` and `ort-sys` 2.0.0-rc.13, matching the
  upstream SDK lockfile. The build uses its checksum-pinned native distribution;
  a dependency lock is not proof of inference or readiness accuracy.

The candidate baseline uses the multilingual checkpoint (standalone source
`convaiinnovations/laya-multilingual@e4e9ddf21a7b1903b7acffd8814ad4307bf63a67`),
whose original SafeTensors hash is
`9d628fd971b700382ac6f65920a86f149777b2e748e0c955fb3b19695aa8f204`.
`core::laya_assets` pins every required original/configuration/conversion asset
separately. The English and typed-decision profiles are diagnostic comparisons,
not silently selected alternatives. The published multilingual long fixture
additionally checks three calibrated Metal answers at 760 state tokens; it
contains no intermediate reference tensors or readiness labels.

`tests/fixtures` contains independently published upstream data, never values
generated by this candidate. The fixed four-question English example checks
token IDs, option markers, raw option/action logits and calibrated answers.
Raw-logit tolerances are declared in `tests/pinned_parity.rs` before comparison;
rounded SDK answers use absolute tolerance 1e-4. Existing Vega tolerances and
historical failed studies are unchanged. These fixtures establish a narrow
numerical comparison, not all-input equivalence, independent human review or
readiness-domain calibration.

`engine::Frontend` rejects oversized input and literal mask-token injection;
it verifies that every state token reaches the upstream sequence builder.
The SDK's truncating and most-confident-window paths cannot silently discard
readiness obligations. Model output retains its reported backend and probability
resolution. Final state binding, storage verification, deterministic gates and
publication permission belong to the Decapod caller.

External fixture tests are opt-in with `DECAPOD_LAYA_REFERENCE_MODEL` pointing
to verified files. They are diagnostic qualification; final product readiness
requires the complete prescribed Decapod validation flow.
