# Closed-loop metacognitive agent governance

**The agent supplies intelligence. Decapod governs convergence. Validation demands proof.**

A coding agent must interpret an evolving request, act on a real repository, detect when its work no longer satisfies its commitments, and correct course. Decapod makes that process observable and governable through repository-native state and agent-facing feedback. The model has **two coupled mechanisms** with different authority.

## 1. Inside the loop: govern the trajectory

```text
original prompt + accepted subsequent instructions
                       ↓
            agent interprets intent
                       ↓
         scopes tasks and proof obligations
                       ↓
             implements the work
                       ↓
   Decapod evaluates governed state and transitions
                       ↓
         feedback → revise → retry ↺
```

Decapod is called at consequential decision and state-transition boundaries. An invocation may approve the requested operation, reject it, or describe the missing precondition and supported remedy. The agent interprets the feedback and changes its work accordingly. It does not need a human to rephrase a routine error as a new prompt.

The **intent baseline evolves through accepted instructions**. The initial request is preserved; subsequent user clarifications change what the agent must deliver, without erasing the provenance of earlier decisions. The repository retains task ownership, scope, context, decisions, and other significant state across sessions and harnesses.

The loop is **metacognitive** because the agent repeatedly evaluates its own plan and implementation against explicit expectations and feedback. Decapod supplies the constraints and durable state that make those comparisons consequential. It does not expose or claim to control every private thought or token generated by a model.

## 2. Outside the loop: execute proof obligations

As part of fulfilling the request, the agent also **designs falsifiable checks** that can demonstrate whether the outcome meets the accepted intent. Decapod requires the relevant claims, checks, and evidence to become explicit, under the Constitution and project policy.

The **validation boundary** runs the required gates against the identified artifact, under the applicable configured rules. It evaluates the evidence and determines whether completion or publication requirements are satisfied.

```text
agent-authored implementation + proof obligations
                       ↓
        required validation gates execute
                       ↓
      current evidence for the exact artifact
                       ↓
         admissible / blocked / unresolved
```

The gates are distinct from the agent's conversational confidence. A proposed test is not an executed test. A completed task is not an accepted artifact. A prior successful check is not automatically proof for a changed commit.

A rejected validation result can return to the agent as another feedback event; the agent must revise and resubmit its actual work. **Iteration is the mechanism of convergence. Validation is the test of that convergence.**

## Why the sequence matters

An agent can take several individually authorized steps and still produce an unsatisfactory result. A trustworthy outcome needs more than isolated permission checks: it needs a recorded trajectory from intent to implementation, clear proof expectations, and validation of the final candidate.

Decapod governs **recorded work and state transitions**, with defined policy and evidence boundaries. It does not claim to infer every internal reasoning step. Likewise, validation establishes what the configured proofs actually demonstrate; it cannot establish semantic correctness that the proof obligations fail to express. When the intent remains ambiguous or evidence is inadequate, the correct outcome is *not proven*, with an explicit blocker or a decision gate.

## In practice

A user asks an agent to change an API, then clarifies a backward-compatibility requirement. The agent records both the request and the clarification, scopes the change, and proposes checks that demonstrate the new behavior **and** compatibility. Decapod rejects unsupported transitions or missing obligations and gives the agent actionable feedback. The agent amends its work and proof design, then submits the candidate to validation. Required gates execute the checks. The resulting evidence is associated with the exact repository state; a failing or missing gate leaves completion unresolved.

This is **closed-loop metacognitive agent governance with proof-backed validation of intent convergence**.
